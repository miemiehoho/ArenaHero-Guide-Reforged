# 40+ 人口优化建议

## 背景与范围

Arena Hero v0.14 已删除人口维护费。当前 Agent 在前 20 个 Unit 使用基础价格扩张，人口达到
20 后则在 Core 满仓时继续生产战斗单位，并保持 `2 Vanguard + 1 Ranger` 的小队编制。

本文聚焦人口超过 40 后的策略和性能扩展。下文保留优化前基线和原始建议，实施状态以本节、
详细设计文档和更新日志为准。

## 当前实现观察（优化前基线）

- 控制模式固定保留 4 名 Worker，其余人口均为战斗单位。人口为 40 时共有 36 个战斗单位，
  即 12 支完整的 `2 Vanguard + 1 Ranger` 小队。
- 0 号小队永久守家，其余完整小队共用 12～32 格方环巡逻范围。随着人口增长，野战小队数量
  增加，但巡逻面积和固定守军数量不会同步增加。
- 发现有守军的敌方 Core 后，所有完整野战小队会前往同一个集结点，容易出现拥堵和长时间
  等待最慢小队的问题。
- A* 单次最多扩展 5000 个节点，多个单位可能在同一 Tick 独立寻路。人口越高，重复寻路越
  容易成为主要性能开销。
- 搜索任务会针对每个任务重复遍历友军视野，任务和单位数量增加后会产生重复计算。
- Core 满仓时，4 名 Worker 都会转入外圈探索；生产恢复后，采集、返航和探索职责可能频繁切换。

## 实现后的行为

- 40 人口起，野战小队按稳定序号分配到 12～32、32～56、56～80 三层巡逻带；0、1 号小队
  守家，2 号小队承担快速反应。
- 有守军的敌方 Core 按每波最多 3 支完整小队分别集结和推进，不再让所有野战小队共用一个
  Rally Point。
- 主动攻击使用共享目标预留：敌方 Worker、战斗单位和 Core 默认最多分配 1、2、3 名攻击者；
  紧急自卫、撤退和家园防守不受上限影响。
- Core 满仓外圈模式下，前两名 Worker 为 `CARRIER`，保留资源任务和载货待命；后两名为
  `SCOUT`，负责 32～64 格外圈探索。
- A* 和搜索覆盖使用 Tick 级短生命周期缓存，动态占位或障碍签名变化时自动失效；诊断摘要
  记录调用、扩展、缓存命中和决策耗时。

## 优化优先级

### P0：建立 40/60 人口压力场景和观测指标

先用可重复的离线场景确认瓶颈，再调整策略。建议至少记录：

- 每 Tick 决策耗时，以及高分位耗时；
- A* 调用次数、累计扩展节点数和缓存命中情况；
- 各小队当前职责、目标、集结等待时间和连续寻路失败次数；
- 生产等待原因，包括资源不足、Core 未满仓、生产格被占用和价格超过容量；
- 长时间无位移、重复争抢目标或集中堵塞的单位数量。

场景应覆盖无敌情巡逻、家园遭袭、有守军 Core 集结、远距离 Core 彻查和生产格拥堵。40 人口
场景用于验证策略扩展，60 人口场景用于暴露寻路和任务分配的性能问题。

### P1：按小队数量动态划分巡逻区域

当前所有野战小队集中在 12～32 格方环，40 人口后容易重复覆盖。可以按小队编号固定分层：

| 野战小队序号 | 建议巡逻范围 |
| --- | --- |
| 1～4 | 12～32 格 |
| 5～8 | 32～56 格 |
| 其余小队 | 56～80 格 |

每支小队继续使用稳定方向扇区，避免每 Tick 重新分配。Core 迁移后再以新位置重建方环和扇区。
这样既保留近家的预警密度，也能让新增人口转化为实际地图覆盖率。

### P1：使用分批集结和攻击波

有守军的敌方 Core 不应要求全部野战小队在一个点到齐。建议：

- 每批包含 2～4 支小队，并为不同批次选择错开的安全集结点；
- 第一批达到最低战力后即可发起攻击，后续批次持续增援；
- 保留 1～2 支小队作为快速反应队，不参与首轮远征；
- 攻击波失去足够战力时撤回重组，避免零散单位持续送入同一入口。

这能缩短首次接敌时间，也能降低三十多个战斗单位同时等待同一 Rally Point 的拥堵。

### P1：让防守力量随人口增长

只保留 0 号小队守家，会让新增战力全部离开 Core。建议按人口调整职责：

| 人口 | 建议防守配置 |
| --- | --- |
| 20 以下 | 1 支守家队 |
| 20～39 | 1 支守家队 + 1 支快速反应队 |
| 40 及以上 | 2 支守家队 + 1 支快速反应队 |

该方案不改变 `2 Vanguard + 1 Ranger` 的生产比例，只改变完整小队的任务分配。快速反应队可以
在近家巡逻、远征增援和拦截敌方 Worker 之间切换。

### P1：跨小队协调目标和伤害

高人口下，多个小队可能同时选择同一低血量目标，造成过量伤害和路径争抢。建议在每 Tick
先生成共享目标分配结果：

- 限制同一敌方单位的近战接敌位和远程攻击者数量；
- Vanguard 优先形成近战屏障，保护 Ranger 的合法射击位置；
- Ranger 根据预计伤害分散射击，目标即将被击杀时转向下一目标；
- 家园防守、攻击波和快速反应队使用同一份目标预留信息。

### P2：降低寻路成本

- 每支小队由队长执行完整 A*，队员优先使用短距离队形跟随；
- 缓存静态障碍下的可复用路径，目标或地图信息变化时再失效；
- 非战斗小队错开巡逻目标更新时间，避免同一 Tick 集中重算；
- 设置 Tick 级 A* 总预算，预算耗尽后沿用旧路径或延迟低优先级任务。

优化时应保留威胁逃跑、近战脱离和生产格疏散等高优先级单位级寻路，不能完全用队长路径替代。

### P2：合并搜索任务的视野计算

当前搜索任务会分别遍历全部友军视野。可以在每 Tick 预计算一次全局可见格集合，供多个任务
共享；如果任务只关心执行小队的覆盖进度，则只合并该小队成员的真实视野。两者都能避免任务
数量增长时重复扫描相同单位和格子。

### P2：细分 Worker 职责

Core 满仓后不必让 4 名 Worker 全部进入外圈探索。建议默认分为：

- 2 名采集/返航 Worker，维持已知资源任务和载货交付连续性；
- 2 名探索 Worker，扩大外圈视野和资源记忆。

Core 满仓且确实无法交付时，载货 Worker 可以临时探索，但生产释放容量后应优先返航。该分工
能够减少满仓状态反复切换造成的无效移动。

### P2：识别动态价格下的生产饱和

动态价格可能最终超过 Core 的最大资源容量。生产前应检查：

```python
unit_cost(next_unit_type, population) > resource_capacity
```

条件成立时进入“生产饱和”状态，停止每 Tick 重复尝试；只有人口下降、下一单位类型变化、价格
规则变化或策略切换时才重新评估。

按当前 4 Worker 和 `2 Vanguard + 1 Ranger` 的生产顺序，本地 SDK 计算示例如下：

| 人口 | Core 容量 | 下一单位 | 价格 | 结果 |
| ---: | ---: | --- | ---: | --- |
| 40 | 200 | Vanguard | 37 | 可生产 |
| 60 | 300 | Ranger | 127 | 可生产 |
| 80 | 400 | Vanguard | 303 | 可生产 |
| 84 | 420 | Ranger | 363 | 可生产 |
| 85 | 425 | Vanguard | 394 | 可生产 |
| 86 | 430 | Vanguard | 394 | 可生产 |
| 87 | 435 | Ranger | 472 | 容量不足，进入饱和状态 |

这些数值依赖当前 SDK 价格规则；规则升级后应由测试重新计算，不能将 87 写死为永久人口上限。

## 推荐实施顺序

1. 补充 40/60 人口离线压力场景和观测指标。
2. 实现动态巡逻分区，先解决新增小队重复覆盖问题。
3. 实现分批集结、攻击波和动态防守职责。
4. 增加跨小队目标预留，减少过量伤害和接敌位争抢。
5. 最后根据压力测试结果优化 A*、搜索覆盖计算、Worker 分工和生产饱和状态。

每一步都应保持现有低人口行为不变，并通过对比场景验证新增逻辑只在相应人口区间生效。
