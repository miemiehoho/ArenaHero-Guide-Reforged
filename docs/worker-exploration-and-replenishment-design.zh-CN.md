# ArenaHero Worker 分区探索与战损补员详细设计

> 设计日期：2026-08-16
> 适用分支：`进攻才是最好的防守`
> 官方基线：Arena Hero 规则 `v0.14`、API `v0.1`、Python SDK `0.2.9`
> 状态：设计阶段

## 1. 背景与问题

当前控制模式在初始阶段固定生产 4 名 Worker，其余人口按 `2 Vanguard + 1 Ranger` 组成小队。
普通资源探索把 Worker 映射到固定 8 个方向，并让所有 Worker 从相同的 12 格方环开始：

- 1～4 名 Worker 可以获得不同方向，但搜索半径都停留在 12～32；
- 超过 8 名 Worker 后必然复用同一方向，多个 Worker 会前往相同或相邻区域；
- `RESOURCE_MEMORY_RADIUS=36` 会丢弃更远资源，即使 Worker 数量增加也不能扩大有效采集范围；
- 人口达到 20 后，Core 未满仓时生产逻辑直接进入 `RESOURCE_WAIT`；战损补员也被这条扩编门槛
  拦住；
- 当前只保证初始 4 名 Worker，没有记录战损前人口，也没有“Worker 至少 12”的恢复目标。

本设计解决两个问题：让 Worker 数量越多时搜索区域越分散、范围越大；让达到成熟人口后的战损
能够自动补员，并保证恢复期 Worker 不少于 12 名。

## 2. 官方约束

实现必须保持以下官方事实：

- 人口只计算当前存活 Unit，不包含 Core；每份新 `state` 是数量权威来源；
- Worker 视野为曼哈顿半径 3，只能 `HARVEST`、`DEPOSIT`、移动、治疗等，不能攻击；
- 每格最多容纳两个占位实体，Core 自己占一个名额；
- Unit 每 Tick 最多移动一格，Agent 每 Tick 只能提交一份完整计划；
- 每 Tick 最多生产一个 Unit，新 Unit 在战斗后出生，本 Tick 不能行动；
- 动态生产价格使用当前存活人口，第 21 个 Unit 才首次涨价；
- v0.14 已删除维护费和欠费伤害，人口超过 20 本身不是停止生产的理由；
- Core 迁移、生产格已满、资源不足、治疗/修盾优先时不能强行生产。

## 3. 目标与非目标

### 3.1 目标

1. 按稳定 UUID 顺序给每名 Worker 分配唯一搜索扇区，超过 8 名后仍不复用扇区。
2. Worker 数量增加时分级扩展普通搜索半径和资源记忆范围，最大到 64 格。
3. 保留资源任务、载货返航、避险、治疗和生产格疏散的现有高优先级。
4. 未发生战损时保留初始 4 Worker、20 人口后的原有满仓扩编门槛。
5. 曾达到 20 人口后检测到人口下降时启动补员：先把 Worker 补到 12，再按现有 2V1R 规则补队。
6. 补员阶段无需等待 Core 满仓，但继续遵守价格、容量、资源和 Core 可用性约束。
7. 补员状态和扇区布局跨重启保持，旧 v9 状态自动迁移到 v10。

### 3.2 非目标

- 不修改官方项目、SDK、协议、地图资源刷新或视野算法；
- 不让多个 Worker 竞争同一个已知资源；现有最小成本一对一资源匹配继续使用；
- 不重写 A*、战斗队、攻击波、治疗或 Core 生存策略；
- 不保证线上一定能支付 12 名 Worker 的动态价格，资源不足时必须等待。

## 4. 阶段 W1：Worker 分区探索与动态范围

### 4.1 连续扇区编号

现有 `worker_sector` 保存 0～7 的八方向编号。改为保存稳定 UUID 排序后的 Worker 序号：

```text
ordered_workers = sort_by_uuid(workers)
worker_sector[worker.id] = index             # 0 .. worker_count - 1
route_offset = index * len(route) // worker_count
```

只要方环路线的 waypoint 数量不少于 Worker 数量，目标便不会重复。当前最小 12 格方环的 waypoint
数量足以覆盖目标 12 名 Worker。Worker 增减导致顺序或数量变化时，重新生成扇区并清理普通/外圈
侦察目标，避免旧分母下的偏移继续生效。

外圈满仓模式也改用实际 `worker_count` 作为分母；只有直接调用旧接口、未提供数量时才保留八方向
默认值，兼容既有单元测试和辅助调用。

### 4.2 随 Worker 数量扩展半径

基础普通搜索半径保持不变，每多 4 名 Worker 增加一个外层方环：

| Worker 数量 | 普通搜索半径 |
|---:|---|
| 1～4 | `12, 19, 26, 32` |
| 5～8 | `12, 19, 26, 32, 40` |
| 9～12 | `12, 19, 26, 32, 40, 48` |
| 13～16 | `12, 19, 26, 32, 40, 48, 56` |
| 17+ | `12, 19, 26, 32, 40, 48, 56, 64` |

每组仍按“由内向外、再向内”的序列循环。新增纯函数：

```text
resource_scout_radii_for(worker_count)
resource_scout_ring_sequence_for(worker_count)
resource_memory_radius_for(worker_count)
```

资源记忆范围至少为当前 36 格基线，并随最大搜索环扩大到 40/48/56/64。满仓外圈扫描本身使用
32～64 格，因此外圈模式下资源记忆范围也至少为 64；离开外圈且 Worker 较少时，再按新范围清理
过远旧资源。

### 4.3 状态优先级不变

探索只处理没有资源任务、没有货物、没有避险/治疗/拦截任务的 Worker。状态顺序继续是：

```text
避险/撤退
-> Core 迁移和生产格疏散
-> 载货返航或近家等待
-> 治疗
-> 已知资源采集与移动
-> 外圈扫描（满仓 SCOUT）
-> 普通分区探索
```

每个 Worker 仍只提交一步移动；目标被永久障碍占用时推进 waypoint，连续三次寻路失败时换目标。

## 5. 阶段 W2：战损检测与补员

### 5.1 补员状态

`AgentMemory` 新增并持久化：

| 字段 | 含义 |
|---|---|
| `population_peak` | 非补员期已观察到的最高存活人口 |
| `replenishment_active` | 是否处于战损恢复期 |
| `replenishment_target_population` | 本轮补员冻结的目标人口 |

触发规则：

1. 正常发展时持续更新 `population_peak`；
2. 只有峰值曾达到 `BASE_AUTO_POPULATION=20` 后，当前人口低于峰值才触发补员；
3. 触发时目标至少为战损前峰值；
4. 若当前 Worker 少于 12，目标再扩大到
   `当前人口 + (12 - 当前Worker数)`，确保补 Worker 不会提前结束；
5. 补员期间再次受损时保持原目标，不因短期回升逐 Tick 推高目标；
6. Worker 至少 12 且人口达到冻结目标后退出补员，并以恢复后的现有人口作为下一轮峰值。

这使初始发展仍只需要 4 Worker；只有成熟人口发生真实下降后才切换到 12 Worker 恢复编制。

### 5.2 生产优先级

补员不覆盖现有安全规则，Core 动作优先级为：

```text
Core HEAL / REPAIR_SHIELD
-> 生产格疏散与 Core 可用性
-> 补员期 Worker 少于 12：SPAWN WORKER
-> 控制模式补齐 2 Vanguard + 1 Ranger 小队
-> 非补员期正常扩编
```

补员期跳过“人口 20 后必须满仓”的门槛，只要治疗预留后的资源足以支付官方动态价格即可生产。
价格超过当前容量时保持 `SATURATED`，资源不足时保持 `RESOURCE_WAIT`，不会提交必然失败动作。

Worker 达到 12 后，现有 `sync_combat_squads()` 会清理死亡 Unit 并稳定重组 2V1R 小队；生产器
优先补 0 号守家队，再补其它不完整小队，最后创建新小队，因而 Vanguard/Ranger 战损也会恢复。

### 5.3 重启与 Core 摧毁

补员状态持久化后，进程重启不会重新忘记战损前峰值。Core 被摧毁并重生时，官方通常返回
1 Worker；只要此前峰值达到 20，下一份 `ACTIVE` 状态就会保持补员，先恢复 12 Worker，再恢复
冻结人口。若是全新安装、没有历史状态，则从当前状态建立峰值，不臆造过去兵力。

## 6. 状态版本 v10

`.arena_core_state.json` 从 v9 升级到 v10：

- v9 的 `worker_sectors` 可以读取；下一次同步改为连续序号并清除旧探索目标；
- v10 不再对扇区编号执行 `% 8`，允许 8 以上的唯一编号；
- 新的峰值、补员目标和激活字段缺失时使用 `0/false`；
- v8/v9 的敌情、小队和彻查任务仍按原版本门槛恢复；
- 不删除 `.env`、旧状态、日志或用户未跟踪文件。

## 7. 日志与统计

生产动作摘要增加：

```text
core spawn WORKER (replenish Workers 5/12 target-population=28)
```

每 Tick 中文统计增加：

- `资源记忆半径`
- `补员激活`
- `历史峰值人口`
- `补员目标人口`

这些字段只用于诊断，不改变计划；API Key、完整状态和凭据仍不得写入日志。

## 8. 测试计划

### 8.1 W1 探索

- 4 名 Worker 获得四等分目标，保持原有覆盖；
- 8、12、16 名 Worker 的扇区编号连续且目标不重复；
- 4/8/12/16 名 Worker 最大搜索半径分别为 32/40/48/56；
- 12 名 Worker 能记录 48 格内资源，49 格资源被清理；
- Worker 增减迁移旧扇区并清理普通/外圈目标；
- 满仓外圈 SCOUT 按实际 Worker 数量错开；
- 资源任务、返航、避险、治疗和路径失败优先级不变。

### 8.2 W2 补员

- 未发生人口下降时，初始控制模式仍在 4 Worker 后生产 Vanguard；
- 峰值 20 降到 19 后激活补员，Core 未满仓但资源足够时生产 Worker；
- Worker 少于 12 时始终优先 Worker；达到 12 后补 Vanguard/Ranger；
- 资源不足、价格超过容量、Core 迁移或生产格已满时不提交生产；
- Worker 达标且人口恢复目标后退出，下一次战损能再次激活；
- Core 摧毁后的 1 Worker 状态继续恢复；
- v9 状态迁移和 v10 round-trip 保留补员字段与 8 以上扇区。
